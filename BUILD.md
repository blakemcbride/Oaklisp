Build instructions for Oaklisp
==============================

Prerequisites
=============

- GCC or Clang
- GNU Make
- Autoconf (>= 2.69) and Automake

Optional:
- LaTeX (texlive, latexmk) for building documentation
- gcc-multilib / glibc-devel.i686 for 32-bit mode on a 64-bit host
- Guile 3 (guile-3.0) to bootstrap from source alone, without prebuilt/

Quick Start
===========

	autoreconf --install
	./configure
	make
	sudo make install

On a 64-bit host this builds a native 64-bit Oaklisp with 62-bit
fixnums.  Oaklisp is self-hosting, so the build has to bootstrap
somehow (see Bootstrapping below); make picks the first of these
that it finds:

- a world image in prebuilt/ (made by "make prebuilt"; not in git),
  or prebuilt bytecode there: nothing beyond a C compiler is needed;
- Guile 3: builds from source alone, which is how a fresh checkout
  and release tarballs -- neither of which carries prebuilt/ -- are
  built.  Takes a quarter of a minute longer.

"make bootstrap" goes on to rebuild the world with itself, so that
what gets installed is self-hosted whichever way it started.

For further details read INSTALL generated by running autoreconf.

Configure Options
=================

Option                    Default   Description
------------------------  -------   -----------
--enable-64-bit           yes       Native pointer size (64-bit on a 64-bit machine)
--disable-64-bit                    32-bit executable on a 64-bit machine (-m32)
--enable-docs             yes       Build LaTeX documentation (turned off,
                                    with a warning, when there is neither
                                    latexmk nor prebuilt/doc)
--enable-ndebug           yes       High-speed mode (sets -DFAST)
--enable-mark-sweep       yes       The mark-sweep collector on a heap of
                                    regions (GC.md); --disable-mark-sweep
                                    builds the copying collector
--enable-threads          no        Native threads; the mark-sweep
                                    collector then runs concurrently
                                    (see Thread Support below)
--enable-cold-linker      no        Build oak-cold-linker, a C version of
                                    the cold linker (see Bootstrapping)
--with-instructions-per-ref=N  4/2  16-bit instructions per code ref:
                                    4 with 64-bit refs, 2 with 32-bit
                                    (see Architectures)
--with-guile[=GUILE]      search    Guile 3 interpreter for the hosted
                                    Oaklisp ("no": none)
--with-readline           check     Edit terminal input with GNU readline
                                    ("no": never; "yes": required)

See ./configure --help for details.  How the world is bootstrapped is
not a configure matter; see Bootstrapping below for the make targets
and variables.

What Gets Built
===============

Two components:

file          | purpose
--------------|----------------------------------------------
oaklisp       | the executable / emulator / virtual machine
oakworld.bin  | pre-built Oaklisp system (read in by the executable)

The world is built in stages from .oak source files:

	new.cold        Cold world (core runtime)
	oakworld-1.bin  Warm boot
	oakworld-2.bin  + macros, bignums, rationals, I/O, development tools
	oakworld-3.bin  + compiler (in compiler-locale), oaklisp-locale exports
	oakworld.bin    the same, set to start in user-locale

Architectures
=============

From Oaklisp's point of view a machine is characterized by

* the size of a reference (word size) in bits, 32 or 64, which
  determines the fixnum range (30 or 62 bits);
* the number of 16-bit instructions packed into each reference in a
  code vector: 2 with 32-bit references, and by default 4 with 64-bit
  ones (--with-instructions-per-ref=2 gives the 32-bit packing, in
  which the other half of each 64-bit reference is unused; it is
  slower, see below, but its bytecode is usable on 32-bit machines).
* the byte order, which matters only for binary world images and the
  running emulator.

These are named as follows, and the names are used for the
subdirectories of prebuilt/, for the --target option, and in the
header lines described below:

	bc2-32     bytecode, 2 instructions per ref, 32-bit refs
	bc2-64     bytecode, 2 instructions per ref, 64-bit refs
	bc4-64     bytecode, 4 instructions per ref, 64-bit refs
	bc2-el32   world/emulator, 2 instructions per ref, little-endian 32-bit
	bc2-eb32   world/emulator, 2 instructions per ref, big-endian 32-bit
	bc2-el64   world/emulator, 2 instructions per ref, little-endian 64-bit
	bc2-eb64   world/emulator, 2 instructions per ref, big-endian 64-bit
	bc4-el64   world/emulator, 4 instructions per ref, little-endian 64-bit
	bc4-eb64   world/emulator, 4 instructions per ref, big-endian 64-bit

Compiled bytecode (.oa files) is independent of byte order, and in
practice of word size too, since the compiler does not fold constants
whose value would depend on it; the word size in the name records
the fixnum range the file's integer constants are assumed to fit,
so bc2-32 bytecode can be used anywhere.  It is specific to the
instruction packing, though: the assembler aligns each inline
reference to a reference boundary, so bc2 and bc4 objects differ in
their padding, and the loader refuses the wrong kind.  Cold worlds
(.cold, the hex text produced by the cold linker) are byte-order
independent but specific to word size and packing.  Binary worlds
(.bin) are specific to byte order, word size and packing.

Each of these files begins with a header line identifying what it is
for, which the emulator, the loader, and the linkers check:

	;oaklisp-bytecode word-size=32 instructions-per-ref=2
	;oaklisp-world format=cold word-size=64 instructions-per-ref=2 chars-per-word=7
	;oaklisp-world format=binary endian=little word-size=64 instructions-per-ref=2 chars-per-word=7

World headers also record how many characters are packed into each
word of a string: 7 with 64-bit references, 3 with 32-bit ones
(a header without the field means 3).

Files without a header are accepted and assumed to be bc2 bytecode,
or, for binary worlds, are identified by their magic bytes (four
\002 or \004 bytes, giving the reference size).

An emulator built for one packing can compile bytecode for the
other, and can link and boot a world for it; only running it needs an
emulator built the same way.  So a bc4 system is bootstrapped from a
bc2 one (or from Guile) in the ordinary way, and a bc2-64 one from a
bc4 one with

	./configure --with-instructions-per-ref=2
	make bootstrap

bc4 is not only smaller (the world image is 9% smaller, the code
vectors in it half the size) but faster: with two instructions in a
64-bit ref the emulator has to step the program counter over the
unused half of each ref, and that costs on every instruction.
Best-of-five times from "make bench" on one machine, in ms:

	benchmark   bc2-64   bc4-64   ratio     bc2-32
	bignum        126       64     0.51       265
	cons          280      158     0.56       171
	dispatch      268      166     0.62      2536
	eval          446      318     0.71       344
	fib           104       76     0.73        85
	format        176      141     0.80       150
	hash          745      611     0.82       999
	sort          306      242     0.79       254
	strings       443      393     0.89       398
	tak            89       70     0.79        76

(bc2-32 has no gap either, which is why it beats bc2-64 on the
code-heavy benchmarks; dispatch and bignum are the 64-bit fixnum
range paying off.)

Within a running system the architecture is available as
`host-architecture`, and the compiler generates code for the fluid
`#*target-architecture`, which defaults to the host and is set by
the --target command line option:

	oaklisp -- --target bc2-32 --compile myfile --exit

Bootstrapping
=============

Oaklisp is self-hosting: the compiler and most of the runtime are
written in Oaklisp, so building the world from .oak source requires a
running Oaklisp.  There are two ways to break the circle.

From source alone, with Guile 3: the Guile-hosted Oaklisp in
src/cold-compiler/ loads the world's own macros and compiler from the
.oak sources and runs them, so the .oa objects, and the cold world
(via tool.oak), come straight from the sources.  This is what a fresh
checkout and the release tarballs made by "make dist" rely on, since
neither carries prebuilt/; it is also how Barak Pearlmutter's Debian
package is built.  Nothing is lost by it: the compiler is
deterministic, so the objects are byte for byte what a native Oaklisp
produces.

With prebuilt material: the prebuilt/ directory ("make prebuilt" makes
it; it is not in git here, and not in tarballs; Barak Pearlmutter's
repository keeps one on its "prebuilt" branch) holds two kinds of
bootstrap material, arranged by architecture:

	prebuilt/src/world/bc2-32/*.oa          compiled bytecode, for bc2 systems
	prebuilt/src/world/bc4-64/*.oa          compiled bytecode, for bc4 systems
	prebuilt/src/world/bc2-el32/oakworld.bin world images
	prebuilt/src/world/bc2-eb32/oakworld.bin
	prebuilt/src/world/bc4-el64/oakworld.bin
	prebuilt/src/world/bc4-eb64/oakworld.bin
	prebuilt/src/emulator/instr-data.c      instruction names for debugging builds
	prebuilt/doc/                           documentation PDFs

Two steps need a running Oaklisp, or a stand-in for one: compiling
.oak to .oa, and linking the cold world.  There are three ways, each
a target in src/world:

	make build-from-old-world
	    An Oaklisp -- the emulator just built running OLD_WORLD --
	    compiles the sources and links the cold world with tool.oak,
	    the Oaklisp linker.  The freshly compiled assembler is loaded
	    into that world first, so an older world can compile sources
	    that use instructions it does not know.
	make build-from-bytecode
	    The prebuilt .oa files are used as they are, and tool.oak
	    links the cold world running in the Guile-hosted Oaklisp.
	make build-from-guile
	    The Guile-hosted Oaklisp in src/cold-compiler/ (see its
	    README) loads the world's own macros, compiler and linker
	    from the sources and runs them.  This needs nothing but
	    Guile 3 and a C compiler, and takes about fifteen seconds
	    (Guile compiles the host to bytecode on first use, cached
	    in src/world/guile-cache).

tool.oak is the linker; porting means porting the emulator.  There
is also oak-cold-linker, a C reimplementation of tool.oak kept as an
independent check on it and for bootstrapping where nothing can run
tool.oak; ./configure --enable-cold-linker builds it, "make
OAK_COLD_LINK=c" in src/world links with it, and "make check"
compares its cold world with tool.oak's when it is present.  It has
to be kept in sync with tool.oak by hand, which is why it is off by
default.

Plain "make" uses the first of these that is possible: an old world
if OLD_WORLD exists, else (with Guile) prebuilt bytecode, else Guile
alone.  OLD_WORLD
defaults to src/world/old-oakworld.bin (where rebuild-world saves the
world, below) if that exists, else prebuilt/'s world for this
machine; any world for the emulator's architecture will do, e.g. an
installed one:

	make OLD_WORLD=/usr/lib/oaklisp/oakworld.bin

The newly built emulator then boots the cold world and loads the
remaining layers.  The result is the same whichever way is chosen:
the compiler is deterministic and reaches a fixpoint, so every route
produces the same objects, and tool.oak links the same cold world in
a world and under Guile ("make check" verifies this).  The methods
can also be combined by hand, e.g. Guile compiling and tool.oak in
an old world linking:

	make -C src/world OAK_COMPILE=guile OAK_COLD_LINK=world

To go on from there to a self-hosted system:

	make rebuild-world

saves the world just built as OLD_WORLD, removes everything the
world build made (clean-world), and makes it all again from scratch
with the saved world (build-from-old-world).  It can be repeated, and
when there is no world to save it rebuilds from the saved one.  One
rebuild on top of any build gives a self-hosted world; a second must
reproduce every object exactly, which is the compiler's fixpoint:

	make bootstrap

builds everything, rebuilds the world with itself twice, and fails
unless the result recompiles its sources to the very objects it was
built from (check-fixpoint), after which "make check" and "make
install" use the self-hosted system.  This is how the Debian package
is built: from source with Guile, then bootstrapped.  A rebuild
takes under a minute.

A world built from prebuilt bytecode reports the version the
bytecode was compiled with (the build warns when that is not the
version being built), which a rebuild also puts right.

One thing the Guile host cannot do is generate src/emulator/instr-data.c,
the instruction name table that only a debugging emulator
(--disable-ndebug) compiles in.  It is generated by the world just
built (and shipped in tarballs), so a debugging build from a bare
source tree needs an old world or prebuilt/ for that one file; the
default high-speed build does not use it.

To build for one word size using an existing Oaklisp of another,
e.g. a 32-bit system on a 64-bit machine with a 64-bit Oaklisp
installed:

	./configure --disable-64-bit
	make OAKLISP=/usr/bin/oaklisp OLD_WORLD=/usr/lib/oaklisp/oakworld.bin

The old system compiles everything with --target bc2-32 and links the
cold world for it, and the new 32-bit emulator boots it.  (The old
system must understand --outdir; an older one is refused, and
prebuilt bytecode or Guile will do instead.)

Building for another byte order requires a cross compiler and a way
to run the resulting emulator, e.g. qemu-user with binfmt support:

	./configure --host=s390x-linux-gnu CC=s390x-linux-gnu-gcc LDFLAGS=-static

With a prebuilt world for that architecture this builds from it
(under qemu); otherwise from bytecode or source with Guile, which
run natively, only the boot running under qemu.

Refreshing prebuilt/
====================

"make dist" leaves prebuilt/ out of the tarball on purpose: releases
are built from source with Guile (or from an installed Oaklisp),
and the material is several megabytes that would go stale.

After building, "make prebuilt" recompiles all the sources into
prebuilt/src/world/bc2-32/ or bc4-64/, whichever this system's
instruction packing calls for, copies the world just built
to prebuilt/src/world/ARCH/oakworld.bin for this machine's
architecture, and refreshes instr-data.c and (if enabled) the PDFs.
The pieces are available separately as "make prebuilt-bytecode" and
"make prebuilt-world" in src/world/, and "make prebuilt" in
src/emulator/ and doc/.  The prebuilt worlds for other architectures
have to be made on (or emulated for) those machines.

Testing
=======

	make check          run the test suite in tests/ (a few minutes)
	make bench          run the benchmarks in tests/bench.sh

The test suite exercises the language, the compiler, world images,
and checks that the world reproduces its own objects, that all cold
linkers agree, and (when Guile is present) that the Guile-hosted
compiler reproduces the objects too.  Failures are detailed in
tests/NAME.log.  "make bench" prints best-of-five CPU times for
eleven small benchmarks, with the longest and the 99th-percentile
stop of one thread for garbage collection in each run (--gc-stats;
GC.md: a global pause where the collector stops the world, a
thread's own root scan with the concurrent collector); see
tests/bench.sh for saving and comparing runs, and for "-p N", which
runs N copies of tak on N OS threads (an emulator with threads)
against the same on one, by the wall clock.

Sanitizers
==========

The suite runs clean under AddressSanitizer with
UndefinedBehaviorSanitizer, the generated C compiled at -O0 (GCC
takes over an hour per generated file with the sanitizers on at
-O1):

	./configure --enable-threads \
	  CFLAGS="-g -O1 -fsanitize=address,undefined -fno-omit-frame-pointer" \
	  LDFLAGS="-fsanitize=address,undefined"
	make
	OAKLISP_NATIVE_CFLAGS="-g -O0 -fsanitize=address,undefined -fPIC -fno-strict-aliasing" \
	  make check

and under ThreadSanitizer, which checks that the concurrent
collector's protocol is expressed in atomics (GC.md, "Shared
words"):

	./configure --enable-threads \
	  CFLAGS="-g -O1 -fsanitize=thread -fno-omit-frame-pointer" \
	  LDFLAGS="-fsanitize=thread"
	make
	OAK_TIMEOUT_SCALE=4 TSAN_OPTIONS=halt_on_error=0:exitcode=0:report_signal_unsafe=0 make check

Its reports go to stderr and the tests run on.  What it reports is
the test programs' own shared variables (threads-stress shares data
between its threads without a mutex on purpose); a report in a
test's output fails native-parity.test, which compares outputs.
OAK_TIMEOUT_SCALE multiplies the time limits the thread and
collector tests run under, for the slowdown; even so
threads-stress's last check, the concurrent definitions, does not
finish under ThreadSanitizer in its time (the checks before it
pass), so that test is expected to fail there.

Thread Support
==============

	./configure --enable-threads

builds the emulator with native (pthread) threads (-DTHREADS), off by
default, and makes the mark-sweep collector, the default build's as
well (-DUSE_MARK_SWEEP), concurrent.  Green threads (DELAY, FUTURE,
PROCESS-RUN-FN) work without it.  With --pthreads N the interpreter,
the bytecode compiler and natively compiled code run on N OS threads
(several compilations can run at once in futures), and make-thread
starts OS threads of its own; see Threads.md.  Unused, the option
costs little:
the mark-sweep collector (a bump allocation into a thread-local
buffer, a sweep that makes one free entry of each run of dead
objects, a heap of 1 MB regions mapped on demand within a budget that
starts at four times the copying collector's heap; with threads, its
cycles on a GC thread of their own, marking in parallel with marker
threads where there are CPUs, --gc-threads) runs the benchmarks
within a few percent of the copying collector's speed, and the thread
support (per-thread registers, the lock-free allocation fast path,
the guarded sections) costs up to about 10% on top.  Measured with
"make bench" on the same world, FAST builds pinned to one core, the
GC thread sharing it (ratio of CPU time to the copying collector's
build, --disable-mark-sweep, 2026-11-04; the threads-with-copying
column from 2026-10-29, its code unchanged since):

	                  THREADS alone  USE_MARK_SWEEP    both
	                  (copying)      (the default)     (--enable-threads)
	tak              1.15           1.02              1.05
	fib              1.10           1.03              1.11
	bignum           1.18           0.94              0.92
	sort             1.10           1.04              1.04
	cons             1.30           0.87              0.87
	strings          1.22           1.01              1.00
	hash             1.09           1.07              1.14
	dispatch         1.06           1.00              1.05
	eval             1.17           1.03              1.07
	format           1.15           1.00              1.07
	compile          1.22           1.00              1.00

These ratios move with the interpreter's code layout as much as with
the collector: between the region-heap commit and the one before it,
the --enable-threads build slowed by 4 to 9% on every benchmark, tak,
fib and dispatch included, which never allocate, and the same sources
built with "-falign-labels=16 -falign-jumps=32 -falign-loops=32" ran
every benchmark at or under the earlier times; the GC thread's commit
moved them back as much the other way, the short pauses' commit (no
change to the interpreter) moved tak, fib and dispatch 5 to 9% again,
and the handshakes' commit moved strings from 1.05 to 1.12 with the
same count of instructions and branches executed (perf: 5.96 billion
each) and 23% more branch mispredictions, while most of the others
moved down.  Take the table as bounds, not as the cost of any one
feature.  Instruction counts, which the layout cannot move (perf
stat over three repetitions of each benchmark, 2026-11-04), put the
mark-sweep collector at 0.5 to 4.5% fewer instructions than the
copying collector on eight of the eleven benchmarks, within 0.4% on
hash and dispatch, and 1.4% more on eval; its peak memory is 0.5 to
4 MB more on the small benchmarks (the 4 MB default budget against a
1 MB heap) and 15% (sort) and 7% (hash) less on the big ones, which
need no second semispace.  Two configured trees of the same sources
(./configure against ./configure --disable-mark-sweep, the same day)
showed the layout's reach: the mark-sweep one ran strings at 1.19x
and tak, which never allocates, at 1.09x, executing 0.5 to 1% fewer
instructions and the same branches, with twice the branch
mispredictions and 1.6 times the instruction-cache misses, nearly
all of them in the interpreter loop; the hand builds above, the
same code linked in another order, ran strings at 1.01x.

With threads in use, "tests/bench.sh -p 4" (four copies of tak, each
on an OS thread, against the same on one thread, wall clock) runs
3.9 times faster, in bytecode and natively alike.

Running Oaklisp
===============

	# Interactive REPL
	oaklisp

	# From the build tree, without installing
	./src/emulator/oaklisp --world src/world/oakworld.bin

	# With explicit world
	oaklisp --world /path/to/oakworld.bin

	# Evaluate and exit; --eval does not output the calculated value, hence the print
	oaklisp -- --eval '(print (+ 1 2) standard-output)' --exit

	# Fancier
	oaklisp -- --eval '(let ((n 40)) (format #t "~%~A! = ~A~%" n (fact n)))' --exit

	# Compile a file
	oaklisp -- --compile myfile --exit

	# Compile a file for another architecture
	oaklisp -- --target bc2-32 --compile myfile --exit

	# Load a file
	oaklisp -- --load myfile --exit

Emulator options go before --, Oaklisp options go after.
"oaklisp --version" reports the emulator's architecture.

Garbage collection options (GC.md): --size-heap N sets the heap in
kilo-refs (512 by default, a budget the mark-sweep heap is mapped up
to as needed and grows past only when the live data does; 128 with
the copying collector); --gc-stats prints the pauses and stalls at
exit, per kind: count, total, maximum, percentiles and a histogram;
--trace-gc 1 to 3 prints each collection, then the budget's changes
and each wait, then every handshake round and the report of
--gc-stats; --gc-threads N sets how many threads mark in parallel in
a threads build (by default one per CPU the process may run on, up to
8).  OAKLISP_OPTIONS carries emulator options to a stand-alone
executable.  The pauses on the benchmarks (GC.md, "Pause
Statistics"): in a threads build a thread's longest stop is the scan
of its own stacks, 0.004 to 0.010 ms, and nothing stops every thread
but a dump; the default build stops for its mark, up to 5.4 ms on
hash, 1.1 on sort and under 0.35 elsewhere; the copying collector for
a whole collection, up to 6.5 ms on hash and 2.4 on sort.

Troubleshooting
===============

"no way to build the world"
    Make found neither an old world, nor prebuilt bytecode, nor
    Guile 3.  Install Guile 3 (guile-3.0; or point configure at one
    with --with-guile=PATH) to build from source alone, or get the
    prebuilt/ directory from another build ("make prebuilt" there),
    or name an installed world: make OLD_WORLD=/usr/lib/oaklisp/oakworld.bin
    (with OAKLISP=PATH if the emulator being built cannot run it).

"world ... is for bc2-el32, this emulator is bc2-el64"
    OLD_WORLD does not match the emulator running it.  Name a
    matching pair with OAKLISP and OLD_WORLD.

"... has 4 instructions per ref, target has 2"
    Bytecode for a different instruction packing cannot be used.

"Integer constant N does not fit in a 30-bit fixnum"
    A file destined for the cold world contains an integer literal
    that is not a fixnum on the target; cold worlds cannot contain
    bignums.  Rewrite the expression, as print-integer.oak does.

32-bit build fails with missing headers
    Install 32-bit development libraries:
    sudo apt install gcc-multilib      (Debian/Ubuntu)
    sudo dnf install glibc-devel.i686  (Fedora/RHEL)

Out of memory with --size-heap
    The argument is in units of 1024 refs.  On 64-bit, each ref is 8
    bytes, so --size-heap 4096 means 32 MB.  The default (1 MB; 4 MB
    with the mark-sweep collector, whose heap is mapped up to the
    size as needed and grows past it only when the live data does) is
    fine for most use.
